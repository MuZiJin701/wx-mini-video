# 目标 AppID 过滤与小程序发现

> 历史规格：保留实施前的问题、确认过程和验收矩阵，不作为当前行为说明，也不随实现持续更新。

GitHub spec：[#4](https://github.com/MuZiJin701/wx-mini-video/issues/4)。当前使用说明见 [README.md](../../README.md)，实现与验收见 [维护指南](../../wx-mini-video-knowledge.md)，版本扩展见 [CHANGELOG.md](../../CHANGELOG.md)。

状态：代码已实现，自动化回归已通过，真实 PC 微信来源覆盖仍待人工验收。测试入口已由用户确认：复用代理响应和 TUI 操作两处现有入口，另行验收真实 PC 微信流量。

2026-10-12 后续扩展：输入与发现界面使用 `Ctrl+D` 切换，媒体界面按 `s` 返回选择；直链音频与匹配 JSON 中的音频链接沿用本规格的严格来源过滤，按 `5` 查看音频。Windows 启动优先使用已安装的 Terminal 并请求 UAC。上述变更统一包含在 v0.1.7；保留以下原始故事和验收矩阵以便追溯。

## 问题陈述

用户希望只保存某个小程序的媒体，但当前输入的会话 AppID 仅用于给候选资源归类。其他小程序或无明确来源的网络请求也会被标成这个 AppID，造成候选列表混杂，用户难以判断和选择目标内容。

不少用户不知道如何查找 AppID。即使补充查找教程，如果 AppID 没有真正限定媒体嗅探范围，资源混杂仍然存在。

## 解决方案

让用户通过手动输入目标 AppID 或小程序发现两种入口选择一个目标，之后只接收请求来源 AppID 与目标 AppID 完整匹配的候选资源。明确属于其他小程序和无法确认来源的资源均排除，接受严格过滤可能漏掉部分目标媒体的取舍。

小程序发现根据代理实际观察到的网络请求列出小程序，以小程序名称和 AppID 展示。名称缺失时显示“名称未识别”，允许用户补填；名称只用于辨认，过滤始终依据 AppID。

小程序发现期间只收集小程序标识，不收集媒体或生成媒体缓存。用户明确选择后，提示重新打开图片或播放视频，再开始媒体嗅探。一次只嗅探一个目标，允许返回选择界面切换；下载正在进行时暂不允许切换。

## 用户故事

1. 作为媒体下载用户，我希望输入目标 AppID 后只看到匹配该小程序的候选资源，以便准确选择想保存的内容。
2. 作为媒体下载用户，我希望其他小程序的资源被排除，以便多个小程序产生请求时列表仍然清晰。
3. 作为媒体下载用户，我希望来源无法确认的资源被排除，以便不会把未知内容误当成目标媒体。
4. 作为媒体下载用户，我希望图片、直链视频和 m3u8 媒体使用相同的目标过滤规则，以便不同媒体类型不会出现归属差异。
5. 作为媒体下载用户，我希望来自已匹配目标的 JSON 接口中的图片和直链视频链接仍能被发现，以便保留已有候选识别能力。
6. 作为知道 AppID 的用户，我希望继续手动输入目标 AppID，以便快速开始媒体嗅探。
7. 作为不知道 AppID 的用户，我希望选择小程序发现入口，以便通过打开小程序找到可选择的目标。
8. 作为小程序发现用户，我希望程序提示我在 PC 微信中打开目标小程序，以便知道如何产生发现所需的网络活动。
9. 作为小程序发现用户，我希望重复请求对应的小程序按 AppID 合并展示，以便不会被重复条目干扰。
10. 作为小程序发现用户，我希望同时看到小程序名称和 AppID，以便辨认候选目标。
11. 作为小程序发现用户，我希望名称无法取得时显示“名称未识别”，以便不会把猜测的名称当成可靠信息。
12. 作为小程序发现用户，我希望能补填小程序名称，以便更容易辨认目标。
13. 作为媒体下载用户，我希望同名小程序仍通过 AppID 区分，以便显示名称不会改变过滤结果。
14. 作为小程序发现用户，我希望明确选择目标后才开始收集媒体，以便背景活跃的小程序不会被自动选中。
15. 作为小程序发现用户，我希望即使只发现一个小程序也由我确认选择，以便避免误选后台小程序。
16. 作为小程序发现用户，我希望选定目标前不会收集媒体或生成媒体缓存，以便发现过程不会带入混杂内容。
17. 作为小程序发现用户，我希望选定目标后收到重新打开图片或播放视频的提示，以便知道为何需要重新触发加载。
18. 作为手动输入用户，我希望确认 AppID 后直接进入目标嗅探，以便不必经过发现步骤。
19. 作为媒体下载用户，我希望能返回目标选择界面切换小程序，以便一次运行可以依次处理不同目标。
20. 作为媒体下载用户，我希望切换目标时清空旧候选和进度，以便当前列表始终对应当前目标。
21. 作为媒体下载用户，我希望切换目标时保留已有本地文件，以便不会失去已下载或可继续下载的内容。
22. 作为正在下载的用户，我希望切换操作给出说明并保持当前目标，以便当前下载能继续完成。
23. 作为媒体下载用户，我希望未发现目标时得到重新打开小程序或改用手动输入的引导，以便知道下一步操作。
24. 作为媒体下载用户，我希望目标列表没有媒体时得到重新加载内容及严格过滤限制的说明，以便能判断是否需要重试。
25. 作为手动输入用户，我希望输入界面和使用说明包含 AppID 查找方法，以便独立完成目标选择。
26. 作为 PC 微信用户，我希望被候选过滤规则排除的请求仍正常转发，以便媒体嗅探不会影响正常使用微信。
27. 作为 m3u8 下载用户，我希望已准入播放列表及其分片和其他依赖继续按现有流程下载，以便目标过滤不会破坏完整下载。
28. 作为项目维护者，我希望需求具有可运行的行为回归检查和真实微信验收步骤，以便知道过滤与选择流程是否实际有效。

## 实现决策

- 复用现有媒体识别、候选资源存储、代理适配、运行时和 TUI 结构，保持单二进制 TUI；不增加与本需求无关的抽象、依赖或授权流程。
- 在共享代理响应入口完成来源解析和准入判断，统一覆盖直接媒体响应与 JSON 候选提取。先判断范围，再读取、远程回补或缓存媒体。
- 首版来源证据采用微信小程序 Referer 的明确格式：HTTPS 来源主机为 servicewechat.com，路径包含独立的 AppID、版本和 page-frame.html。解析来源 URL 后完整比对请求来源 AppID 和目标 AppID；不允许子串匹配、相似域名或任意位置出现 AppID 就放行。格式不合法或无法解析时按来源不明排除。
- 用户输入的 AppID 去掉首尾空白且不能为空；名称允许为空。沿用已有配置字段及预填能力，但选择目标前不开始媒体收集。不能把空目标解释为接收所有媒体。
- 小程序发现模式允许代理在尚未选择目标 AppID 时运行，但只登记可识别的小程序标识，按 AppID 去重，不读取媒体正文用于候选提取，也不生成媒体缓存。
- 手动输入与发现选择最终进入相同的目标过滤路径。发现阶段即使只有一个目标也需要用户明确选择；选定后提示重新加载媒体。
- 小程序名称必须与 AppID 明确关联才能作为已有名称展示；当前可依赖用户填写或补填。缺失时显示“名称未识别”，不得用媒体标题或共享 CDN 域名猜测小程序名称；本次不承诺仅凭任意 AppID 自动查询名称。
- 对已匹配目标的 JSON 接口，保留提取图片和直链视频的能力及来源信息。维持 JSON 中 m3u8 链接不直接加入列表的范围，等待实际观察到匹配来源的播放列表响应。
- 来源未知的独立媒体请求不放行。首版不关联其他请求中的媒体 URL，也不因共同 CDN 域名扩大范围。候选过滤不修改正常转发结果。
- 运行时必须支持发现、目标选定和切换的完整状态变化。当前代理插件捕获启动时的目标，仅修改运行时设置会造成过滤目标与列表目标不一致，实施时必须一并解决；切换完成后，旧目标的在途响应不得重新填充当前列表。
- 一次只激活一个目标。切换清空旧目标候选、选择位置和进度，保留已下载文件、历史、部分下载文件和已有缓存；重新选择后重新加载媒体。
- 下载正在进行时拒绝目标切换并提示原因，不取消下载。已准入的 m3u8 下载及其依赖沿用现有下载流程，不要求每个下载依赖重新提供请求来源 AppID。
- 更新输入引导、发现及空列表提示，以及受影响的中文、英文使用说明和维护文档。说明严格过滤的覆盖限制与名称补填行为，不把尚未具备的能力写成已支持。

## 测试决策

测试只验证用户可见结果和外部副作用，不锁定内部帮助函数、字段布局或具体实现。优先复用现有两处测试入口，不为本功能预建泛化的测试架构；这两处入口和真实微信验收已由用户确认。

1. **代理响应入口**：使用已有代理上下文测试替身驱动真实响应处理，观察候选列表、发现结果、缓存文件和 HTTP 请求。覆盖匹配、不匹配、缺失及非法来源，确保被排除的响应不读取媒体正文用于提取、不写媒体缓存、不发起播放列表回补。
2. **TUI 操作入口**：延续已有按键或消息输入、状态和界面结果的测试模式，覆盖手动输入、发现、显示与补填名称、明确选择、切换、进度清空及下载中拒绝切换。复用真实运行时与候选存储；仅在必要处隔离会改动系统代理或证书的环境操作。
3. **测试先例**：现有测试已经通过代理响应验证直接 m3u8 缓存、JSON m3u8 跳过，并通过 TUI 操作验证 AppID 必填、可选名称、分类切换和下载进度。更新这些相关 fixture 的来源信息，防止严格过滤后测试只因候选全部被丢弃而假通过。
4. **目标切换回归**：在相同处理链先后提交不同来源 AppID 的响应，验证切换后仅保留新目标；覆盖旧目标在途响应与新目标请求交错的情况。发现与切换不能只测界面状态而遗漏实际过滤结果。
5. **自动验证**：实施后运行 go test -count=1 ./... 和 go vet ./...；文档运行 git diff --check。若涉及 Windows 分发，按项目构建检查验证包内容。
6. **真实 PC 微信验收**：分别检查目标图片、直链视频、m3u8 和接口请求的来源信息，观察多个小程序同时活跃、发现并选择目标、手动输入及切换流程。记录来源缺失导致的覆盖限制，不能将模拟请求测试通过视为已验证真实覆盖；不在 issue、文档或测试 fixture 中公开鉴权头、Cookie 或签名媒体 URL。

### 验收矩阵

| 场景 | 预期结果 |
| --- | --- |
| 请求来源 AppID 与目标完整匹配，响应为支持的图片、直链视频或 m3u8 | 收集候选；m3u8 沿用现有缓存流程 |
| 请求来源 AppID 明确属于其他小程序 | 不收集候选、不生成媒体缓存、不发起媒体回补 |
| 来源信息缺失、非法或不可解析 | 不收集候选、不生成媒体缓存、不发起媒体回补 |
| 相似 AppID、相似来源域名，或 URL 查询等任意位置出现目标 AppID | 不能据此放行 |
| 与目标共用 CDN 域名但缺少匹配来源 | 不收集候选 |
| 已匹配目标的 JSON 接口返回图片和直链视频链接 | 收集这些候选并保留接口来源信息 |
| JSON 返回 m3u8 链接 | 跳过，待观察到匹配来源的实际 m3u8 响应 |
| 小程序发现阶段收到普通接口或媒体响应 | 可登记请求来源 AppID；不提取媒体或生成媒体缓存 |
| 同一 AppID 出现多次 | 发现列表只保留对应的一个小程序条目 |
| 仅发现一个小程序 | 等待用户明确选择 |
| 小程序名称缺失 | 显示“名称未识别”和 AppID，允许补填并选择 |
| 不同 AppID 使用相同名称 | 仍按 AppID 区分和过滤 |
| 手动输入有效的非空 AppID | 直接进入目标嗅探，适用相同过滤规则 |
| 用户选定目标 | 提示重新加载媒体，此后开始目标候选收集 |
| 从目标 A 切换到 B | 清空旧列表和进度，新资源只按 B 过滤；本地文件保留 |
| 切换到 B 后收到 A 的在途响应 | 不得恢复 A 的候选或将其标为 B |
| 下载进行中尝试切换 | 显示说明、维持当前目标，下载继续 |
| 请求被候选过滤规则排除 | 正常网络转发继续 |

## 范围外

- 跨请求媒体 URL 关联，以及按共享 CDN 域名推断资源归属。
- 扫描微信已安装或历史使用的全部小程序。
- 保证任意 AppID 都能自动获取名称，或增加小程序管理凭证、第三方授权和名称查询服务。
- 同时嗅探多个选定目标、自动选择唯一发现目标、在选择前收集或缓存媒体。
- 下载进行中切换目标、自动取消下载、切换时删除本地文件。
- 从 JSON 中新增 m3u8 下载入口，或重写既有媒体下载、受管 ffmpeg 和代理实现。
- 新增持久化名称映射、额外配置选项或其他未讨论功能。
- 本次 spec 编写不包含功能实现、代码发布或真实微信环境操作。

## 补充说明

- 本规格落实已逐项确认的严格过滤、双入口、名称缺失降级、单目标切换及先选择后嗅探规则；用户已确认测试入口。
- 严格过滤优先保持列表清晰，可能漏掉缺少请求来源 AppID 的目标媒体；名称无法自动取得时通过用户补填完成辨认。
- 目前代理能观察请求 URL 和请求头，没有微信窗口或小程序运行实例信息。真实 PC 微信各媒体路径是否提供来源信息，尚需实施阶段验收。
- 微信账号信息接口返回 AppID 等信息但不返回名称；已核对的基本信息接口可返回名称，但需要凭证或授权。这不构成任意 AppID 的匿名名称查询能力。
- 官方来源参考：[微信小程序请求 Referer 格式](https://cloud.tencent.com/document/product/1722/112278)、[wx.getAccountInfoSync](https://developers.weixin.qq.com/miniprogram/dev/api/open-api/account-info/wx.getAccountInfoSync.html)、[获取小程序基本信息](https://developers.weixin.qq.com/doc/oplatform/openApi/OpenApiDoc/miniprogram-management/basic-info-management/getAccountBasicInfo.html)。
