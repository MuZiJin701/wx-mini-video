# HTTP-FLV 直播流识别与持续录制

状态：已实施（2026-10-25）。需求来自用户反馈：小程序直播的 HTTP-FLV 直链被当作普通视频下载。本日后续[需求修订](../tui-alignment-requirements.md)将直播设为独立页签和目录、m3u8 分类改称分段媒体；该分类与目录修订已实施，差异与后续项见文末“实施记录”。

## 背景

小程序直播常用 HTTP-FLV：地址形如 `.../<id>_esd.flv`，响应为 `video/x-flv`，用 chunked 长连接持续下发，没有 `Content-Length`、没有总时长、没有结束点。旧实现的问题：

- `.flv` 不在 `ClassifyByURL` 的扩展名表里，也没有 FLV Content-Type 分支；JSON 候选只能走「字段名强相关」的低置信推断，`kind=video`、`suffix=.mp4`，文件名变成 `xxx.flv.mp4`，播放器按 mp4 解析失败。
- 直链下载只做 `io.Copy` 到 EOF，并用响应声明的长度做完成校验；直播流既不结束也没有长度，下载进度显示未知大小，只有用户强制退出才会停止，且退出后只留下不可直接播放的 `.part`。
- 它不会出现在 m3u8 分类：二者是不同协议（HTTP-FLV vs HLS），小程序播放器本次没有请求 m3u8，代理里也就没有可缓存的播放列表。

## 决策

- **分类与展示**：`.flv` 扩展名与 `video/x-flv`、`video/flv`、`application/x-flv` 仍使用 FLV 媒体识别与下载路径，后缀 `.flv`；直播候选在界面中只进入“直播”和“全部”，不混入普通“视频”。疑似直播明确标记，确认是有限文件后归回视频；独立页签不要求新增传输处理类型。
- **分类目录**：实际直播录制保存到 `直播/`，普通有限 FLV 保存到 `视频/`；晚确认直播同样修正最终路径和历史记录，见修订后的 [ADR 0012](0012-per-appid-download-layout.md)。
- **判定**：候选新增 `Live bool`。响应为 FLV Content-Type 且长度未知（chunked）时标记为直播；`.flv` 地址在 JSON/H5 路径（尚无响应信息）先按「疑似直播」标记，真实响应到达后以响应为准（带 `Content-Length` 则取消标记）。下载时再用响应头与响应体开头的 `FLV` 魔数确认，避免把普通分块下载误判成直播。
- **录制语义**：疑似直播不发 Range、不续传；确认直播后进度状态为 `recording`，`Total=-1`，跳过响应长度校验；服务端结束或断开时把已录内容提交为最终文件。用户按 `x` 或确认退出时取消下载上下文，把已录内容从 `.part` 提交为 `.flv`，返回 `ErrRecordingStopped` 并写入 `history.jsonl`。异常断流（`ctx` 未取消时的断网、`unexpected EOF` 等）同样提交已录内容并写入历史，返回 `ErrRecordingInterrupted` 并在界面报告原因；提交失败时保留 `.part` 并原样暴露错误。只有真正的上下文取消才折算为「已停止」，保存失败不得被伪装成正常停止。普通下载被用户停止时保留 `.part`，返回 `ErrDownloadStopped`。
- **重试**：默认命名的下载在重试时按候选标识反查遗留 `.part`，复用前按实际内容判定：以 `FLV` 魔数开头的是未保存直播录制，一律不复用，并为新录制分配独立文件名；选名在**同一个循环**里同时避开已存在的成品与同候选 `.part`（含 `_2` 等重名变体），续传则直接使用遗留基名，避免分两步改名后二次撞上旧 `.part`。普通下载继续复用续传。直播与指定文件名不复用旧文件，防止覆盖上一次录制。只有下载时才确认为直播的候选，产物后缀修正为 `.flv`。
- **不设录制上限**：本次不按时间或大小自动停止，停止完全由用户触发；后续如需上限再扩展配置与界面。
- **退出流程**：下载/录制中确认退出不再直接恢复代理退出，而是先取消下载、等 `downloadMsg` 收尾（保存直播录制、保留普通下载 `.part`），再进入退出流程。只有收尾结果为正常完成、`ErrRecordingStopped`、`ErrDownloadStopped` 或已保存的 `ErrRecordingInterrupted` 时才继续退出；保存失败等真实错误取消自动退出，保留错误界面与现场。
- **展示**：候选「类型」列、日志与详情显示「直播流」，详情依据为「HTTP-FLV 直播流（URL/响应识别）」；录制中状态行显示已录大小与「按 x 停止并保存」，行尾状态显示「录制中」；退出确认文案区分普通下载与直播录制。
- **分段媒体与支持范围**：m3u8 的界面分类称为“分段媒体”，产物与缓存进入 `分段媒体/`；现有播放列表获取和合并处理保留。本轮不新增 HLS 持续直播录制，无 `#EXT-X-ENDLIST` 的列表仍可能只保存当前快照，不能因新增直播页签宣称已支持 HLS 直播录制。

## 备选方案

- **新增独立传输类型 `kind=live`**：直播状态与传输类型分开表达；独立页签和直播目录可复用直播标记及实际响应判定，无需为界面筛选增加新的传输处理分支。
- **只按 Content-Type 判定**：JSON/H5 候选没有响应头，无法在列表中提前提示；补上 `.flv` URL 启发式，并由真实响应修正。
- **默认录制上限**（如 30 分钟/1 GB）：用户明确要求先不设置；未经确认截断内容比无限录制更糟。
- **保持原行为（当普通视频下载）**：后缀错误、下载永不完成、退出只留 `.part`，正是本次要修的问题。
- **改用 ffmpeg 录制 FLV**：直连录制不需要外部进程，也不依赖 ffmpeg；ffmpeg 只在 m3u8 流程使用。

## 后果

- `.flv` 不再落入「未知二进制」兜底，文件名后缀正确；用户可用 ffmpeg/VLC 播放或转封装成 mp4。
- 直播没有长度校验，长时间录制会持续写盘；用户需自行按 `x` 停止，文档与状态行必须明确说明。
- 断流与保存失败是不同语义：前者尽力保全已录内容并报告原因（`ErrRecordingInterrupted`），后者必须暴露真实错误并保留 `.part`；两者都不能被统一的取消映射掩盖。
- 重试续传依赖按候选标识反查 `.part`；直播录制（按 FLV 魔数识别）永不复用，旧录制若因保存失败留下 `.part` 需用户自行恢复；新录制分配独立文件名，避免同一秒重试覆盖。
- 退出收尾失败不能直接退出：否则用户看不到保存错误，也无法处理 `.part`；取消自动退出后由用户决定再次退出。
- 停止/退出路径依赖可取消的下载上下文（`downloadCancel`）与「退出前等待下载收尾」的状态（`quitAfterDownload`），测试需覆盖录制停止、退出收尾与普通下载停止。
- `LooksLikeLiveFLV` 对 `.flv` 地址是启发式：若 CDN 用 `.flv` 提供有限文件，列表会先显示「直播流」，下载时以 `Content-Length` 与 FLV 魔数修正为普通下载（文件名仍是 `.flv`，不影响内容）。
- HLS 直播仍不在识别范围内，README 与知识文档需注明当前只覆盖 HTTP-FLV。

## 实施记录（2026-10-25）

- 分类与展示已实现：新增直播独立页签 `5 直播`（页签顺序 `1 全部 / 2 图片 / 3 视频 / 4 音频 / 5 直播 / 6 分段媒体`），直播候选只进入“全部”和“直播”；疑似直播保留“直播流”标记；响应确认有限 FLV 后由 `Store.SetLive` 回写并归回“视频”。
- 目录已按修订后的 ADR 0012 实现：实际直播录制保存到 `直播/`，普通有限 FLV 保存到 `视频/`，晚确认直播同样修正最终路径与 `history.jsonl`。
- 录制语义、停止/断流保存、重试不复用未保存录制、退出前等待收尾与保存失败保留现场均按决策实现，并有对应回归测试。
- 界面联动：直播状态被下载响应修正而移出当前分类时，选中会清空并提示重新选择，避免误操作另一条资源；详情保留「HTTP-FLV 直播流」识别依据。
- 实现差异/后续项：HLS（m3u8）持续直播录制**仍不支持**，本轮不新增该能力；无 `#EXT-X-ENDLIST` 的播放列表可能只保存当前快照并合并为 mp4，文档不得表述为已支持 HLS 直播录制。
